# 05 — AI Design

> The AI calls (three core calls in 1.0, plus cover letters; interview prep kits, bullet coach, and the free tool), their exact input and output contracts, the prompts, the **fabrication guard**, scoring, cost, and evals. This is the product's core, so treat changes here like schema changes: update this doc, run evals, then merge.

## The calls

`src/lib/ai/pricing.ts` holds per-model $/MTok (input, output, cache read, cache write) and `estimateCostMicros(model, usage)`, which `runStructured()` uses to fill `AiCall.costMicros`. Update it when prices change.

Thinking tokens count toward `max_tokens`, so leave headroom. The model IDs above were current on the Claude API docs as of October 2026. Re-check the models page before launch.

## `runStructured()` — the only way to call the AI

`src/lib/ai/run.ts`. Feature code never imports `@anthropic-ai/sdk` directly.

```ts
type RunArgs<S extends z.ZodTypeAny> = {
  kind: AiCallKind;                         // from the Prisma enum
  userId: string | null;                    // null ONLY for FREE_TOOL
  usedBonusCredit?: boolean;                // set by the caller from the quota check
  system: string;
  content: Anthropic.ContentBlockParam[];   // user message content blocks
  schema: S;
  refId?: string;                           // jobId / resumeId / coverLetterId / prepKitId
};

type RunResult<T> =
  | { ok: true; data: T }
  | { ok: false; code: "AI_FAILED" | "AI_REFUSED" | "AI_TRUNCATED" };

export async function runStructured<S extends z.ZodTypeAny>(args: RunArgs<S>): Promise<RunResult<z.infer<S>>>
```

Implementation requirements:
1. Look up `AI_TASKS[kind]`.
2. Call `client.messages.create({ model, max_tokens, system, messages: [{ role: "user", content }], output_config: { format: zodOutputFormat(schema), effort } })`. Imports: `zodOutputFormat` from `@anthropic-ai/sdk/helpers/zod`. (If the helper rejects a Zod 4 schema, fall back to `jsonSchemaOutputFormat(z.toJSONSchema(schema))` from `@anthropic-ai/sdk/helpers/json-schema`.) Read the first text block and parse it in this module. Do not use `messages.parse`: its parser throws away the message when one field fails Zod, which drops a usable analysis and records no tokens. A caller may pass `normalize` to repair optional fields before the schema check.
3. `stop_reason === "refusal"` → `AI_REFUSED` (stage `provider`). `stop_reason === "max_tokens"` → `AI_TRUNCATED` (stage `validation`). JSON that still fails the schema after `normalize` → `AI_FAILED` (stage `validation`). A thrown API error → `AI_FAILED` (stage `provider`). Usage on a returned message is stored even when validation fails. A thrown error stores zero tokens.
4. **Always** insert an `AiCall` row (success or not) with `model`, `inputTokens`, `outputTokens`, `cacheReadTokens`, `cacheWriteTokens` (from `usage`), `durationMs`, `costMicros`, `errorCode`, `refId`, `usedBonusCredit`. On success with `usedBonusCredit`, decrement the bonus credit in the same transaction (see `04-DATA-MODEL.md` → Quotas).
5. Client config: `timeout: 120_000`, `maxRetries: 2` (the SDK retries 429/5xx).
6. **Never log** prompt content, file content, or model output. Log `kind`, ids, codes, tokens, duration, and `stage` (`ok`, `provider`, or `validation`). A validation log may include issue `path` and `code` only.

### Structured-output schema rules (API limits)

AI output schemas are **separate** from the stored/DB schemas and kept loose, because the API's JSON Schema support excludes `minLength`/`maxLength`, numeric min/max, and array sizes beyond `minItems` 0/1. Limits and cleanup are enforced **in code after** the call.

- Use only: `z.object`, `z.string()`, `z.boolean()`, `z.array()`, `z.enum()`, `.nullable()`.
- No `.min()`, `.max()`, `.url()`, `.regex()`, `.default()`, or recursion in AI schemas.
- Optional values: `.nullable()` (not `.optional()`), so every key is always present.

Each prompt module (`src/lib/ai/prompts/<kind>.ts`) exports `SYSTEM`, `buildContent(...)`, and `OutputSchema`.

## 1. IMPORT — resume → library

### Input
- **PDF:** send natively as a document block (no PDF parser needed; Claude reads text and layout):
  ```ts
  { type: "document", source: { type: "base64", media_type: "application/pdf", data: base64 } }
  ```
  followed by a text block: `"Extract this resume into the schema."`
- **DOCX:** `mammoth.extractRawText({ buffer })` → text block wrapped in `<resume>…</resume>`.
- **Pasted text:** text block wrapped in `<resume>…</resume>`.
- Reject text under 200 or over 40,000 characters, and files over 5 MB.

### Output schema (`ImportOutput`)

```ts
z.object({
  profile: z.object({
    fullName: z.string().nullable(),
    headline: z.string().nullable(),
    email: z.string().nullable(),
    phone: z.string().nullable(),
    location: z.string().nullable(),
    links: z.array(z.object({ label: z.string(), url: z.string() })),
    summary: z.string().nullable(),
  }),
  entries: z.array(z.object({
    kind: z.enum(["EXPERIENCE","PROJECT","EDUCATION","CERTIFICATION","VOLUNTEER","OTHER"]),
    title: z.string(),
    organization: z.string().nullable(),
    location: z.string().nullable(),
    startDate: z.string().nullable(),   // "YYYY-MM" | "YYYY" | null
    endDate: z.string().nullable(),
    isCurrent: z.boolean(),
    url: z.string().nullable(),
    bullets: z.array(z.string()),
  })),
  skills: z.array(z.object({ name: z.string(), category: z.string().nullable() })),
  warnings: z.array(z.string()),        // shown on the review screen
})
```

### System prompt (draft)

```
You extract resumes into structured data for a resume-tailoring app.

Rules:
- Copy text faithfully. Do not rewrite, improve, summarise or merge bullets. Only fix obvious
  extraction artifacts (broken hyphenation, stray bullet symbols, doubled spaces).
- Never invent information. If a field is not present, use null (or [] for lists).
- Dates: "YYYY-MM" when month and year are known, "YYYY" when only the year is known, otherwise null.
  "Present"/"Current" → endDate null and isCurrent true.
- kind: paid roles, internships and contract work → EXPERIENCE; personal/academic/open-source
  work → PROJECT; degrees/diplomas/courses → EDUCATION; certifications/licences → CERTIFICATION;
  unpaid community work → VOLUNTEER; anything else → OTHER.
- Every bullet belongs to exactly one entry, in original order. Paragraph-style descriptions
  become one bullet per sentence.
- Skills: include items from any skills section, plus technologies/tools explicitly named in
  bullets. One skill per item ("React", not "React/Redux" — split those). Use a short category
  ("Languages", "Frameworks", "Tools", "Cloud", "Data", "Soft skills") or null.
- profile.headline: the line under the name if present, else null. Do not create one.
- Add a warning for anything you could not place or were unsure about (e.g. "Dates for 'Acme'
  were unclear").
```

### Post-processing (code, `features/import/extract.ts`)

1. Trim all strings; drop empty bullets and entries with an empty title.
2. Dates not matching `^\d{4}(-(0[1-9]|1[0-2]))?$`, or outside 1900–2099, → null (add a warning). "Present", "Current", "Now", or "Ongoing" on the end date → `endDate` null and `isCurrent` true, with no warning. If `isCurrent` is true, clear `endDate`. If the end date is before the start, clear the end date and warn.
3. Skills: dedupe by `nameKey`; drop names over 50 characters.
4. Bullets over 400 characters → keep, and set `long: true`. A bullet over 2,000 characters is cut to 2,000, still flagged, with a warning. The confirmation and the review both hold a bullet this long until it is shortened or left out.
5. Links: keep only `http(s)://` URLs; prepend `https://` to bare domains. The same rule applies to an entry URL. Drop URLs still over 300 characters.
6. Clamp the rest to the library caps, and warn when something was shortened: profile name 80, headline 120, email 254, phone 40, location 80, summary 2,000, link label 40, entry title and organization 120, entry location 80, skill category 40. Keep at most 5 profile links.
7. Return to the client. An empty library shows a confirmation first (**Save to library**, or **Review and edit first**). A library that already has entries or skills opens the full review, including Append or Replace. **Nothing is saved until `commitImport`.** `extractResume` checks the IMPORT quota before the model call. A bad file is `VALIDATION` and does not use quota.

## 2. ANALYZE — posting → requirements

### Input
`<posting>{rawText truncated to 15,000 chars}</posting>`

### Output schema (`AnalyzeOutput`)
Same as `JobAnalysis` in `04-DATA-MODEL.md` but **without** `requirements[].id`. Code assigns `r1…rN`, caps requirements at 20 and keywords at 30, and dedupes keywords case-insensitively.

### System prompt (draft)

```
You analyse job postings for a resume-tailoring app. Extract only what the posting states.

- title, company, location: as written. If the company is not named, use "Unknown company".
- seniority: infer from title and years of experience; "unknown" if unclear.
- summary: 1–2 plain sentences describing the role.
- requirements: 5–20 distinct, concrete requirements. Split compound lines
  ("React and TypeScript" → two requirements). importance "must" for required/minimum
  qualifications, "nice" for preferred/asset/bonus. Skip generic filler ("team player",
  "fast-paced environment") unless it is the only requirement of its kind.
- keywords: 10–30 terms an applicant-tracking system would match: tools, technologies,
  methods, certifications, domain terms. Use the exact spelling from the posting.
- workMode, employmentType, salary (min/max/currency/period), referenceNumber
  (requisition / competition / selection process number): only if stated; otherwise
  UNKNOWN / null. Never estimate a salary amount. When an amount is stated and no
  currency is named, use CAD if the role is in Canada and USD if the role is in
  the United States; otherwise null. Do not default a Canadian role to USD.
```

Post-processing: before the schema check, optional values outside the enums are repaired and the rest of the analysis is kept. Employment type `UNKNOWN`, or any unstated arrangement, becomes null (`full-time` and the same words for the other types are kept). Seniority outside the list becomes `unknown`, and `junior` is `entry`. Work mode outside the list becomes `UNKNOWN`. A salary period of annual or yearly becomes `YEAR`, and hourly becomes `HOUR`. Any other period, or a salary that is not an amount, becomes null. A stated amount written as `CA$94,000` is read as `94000`. Requirement importance `required` is `must`; other labels that are not `must` are `nice`. A response that is not JSON, or that has no title, company, summary, requirements, or keywords, is a validation failure and is not saved. The analysis then pre-fills `Job.title`, `company`, `location`, `workMode`, `employmentType`, `salary*`, and `referenceNumber` only where the user hasn't already set them. A blank URL is filled from the posting when it contains one link, or a link next to “apply”; a URL the person typed stays. The pasted posting is stored unchanged. Salary amounts are still kept only when the posting states them. Currency is the code the posting names (`CAD`, `C$`, `USD`, `US$`, and the same for GBP, EUR, AUD, NZD). When an amount is stated and no currency is named, a role placed in Canada — by the title, the location (including a province or `City, ON`), or a location phrase in the posting — is stored as CAD. A model `USD` on that role is replaced with CAD. An explicit USD, or any other stated code, is kept. A salary the user already saved is not overwritten. If preparing or saving the analysis throws, the job stays FAILED, the charge is released, and the log stage is `extraction` or `persistence`.

## 3. TAILOR — library + job → tailored resume

### Library serialization (`features/library/serialize.ts`)

Short refs instead of UUIDs: fewer tokens, and the model doesn't mangle them. `serializeLibrary()` returns `{ text, snapshot }`, where `snapshot` is the `LibrarySnapshot` (ref → DB id), stored on the Tailor. Example (illustrative content, not real data):

```
PROFILE
Name: Morgan Example | Headline: Data & reporting analyst
Default summary: …

E1 | EXPERIENCE | Junior Program Officer | Canada Revenue Agency | Ottawa, ON | 2023-11 – Present
  E1.B1 id=<bullet id>: Built and maintained 14 IBM Cognos reports used by a 20-person processing team.
  E1.B2 id=<bullet id>: Automated monthly business review workbook with Excel VBA, cutting prep time from 2 days to 3 hours.
E2 | PROJECT | Booking bot | — | — | 2025-03 – 2025-04
  E2.B1 id=<bullet id>: Wrote a Python/Playwright bot that …
E3 | EDUCATION | B.CS. Honours | Carleton University | Ottawa, ON | – 2023
SKILLS
  S1 id=<skill id>: Python (Languages)
  S2 id=<skill id>: SQL (Languages)
  S3 id=<skill id>: IBM Cognos (Tools)
```

`serializeLibrary(library, takenAt)` is pure. The caller passes `takenAt` (stored on the snapshot); the function does not read the clock. The snapshot is the ref map the tailor pipeline stores.

The prompt text is one record per line. A bullet line is `  E1.B1 id=<bullet id>: …` and a skill line is `  S1 id=<skill id>: …`. The id is the stable library id. The `E` and `S` labels stay the citations the model returns. Email, phone, location, profile links, and entry URLs stay on the snapshot and are left out of the text. An empty name, headline, summary, title, organization, location, or date range is an em dash (`—`). A range with no start and an end date is `– 2023` (en dash). A current role is `{start} – Present`, or `Present` when the start is missing. Dates in the text are the stored `YYYY` or `YYYY-MM` strings. Newlines in a summary or bullet become one space in the text; the snapshot keeps the original string. A skill with no category has no parentheses. A `|` in user text is left as written. The `SKILLS` heading is always present.

Ordering: entries grouped by kind (EXPERIENCE, PROJECT, EDUCATION, CERTIFICATION, VOLUNTEER, OTHER). Inside a kind, current roles come first, then end date descending, then start date descending. A year with no month counts as December on an end date and January on a start date (`2024` is newer than an end of `2024-06`, and ties an end of `2024-12`). A missing or unparseable end date on a past role sorts after every dated end. Equal dates break by `sortOrder`, then id. Refs are assigned after that order: `E1`… across all entries, `E1.B1`… by bullet `sortOrder`, `S1`… by skill `sortOrder`.

### Input content (user message)

```
<library>
{serialized library}
</library>

<job>
Title: {title} | Company: {company} | Seniority: {seniority}
Requirements:
  r1 [must][skill] 3+ years of React
  r2 [nice][certification] AWS certification
  …
Keywords: React, TypeScript, AWS, CI/CD, …
</job>

<posting>
{rawText truncated to 12,000 chars}
</posting>

<options>
Target length: up to 1 page. Stop when another line would not add distinct evidence. Two pages is a ceiling, not a quota.
Emphasis from the candidate: {emphasis or "none"}
</options>
```

### Output schema (`TailorOutput`)

```ts
z.object({
  summary: z.string(),
  entries: z.array(z.object({
    ref: z.string(),                                  // "E1"
    bullets: z.array(z.object({
      sourceRefs: z.array(z.string()),                // one to five, same role, e.g. ["E1.B1","E1.B2"]
      text: z.string(),
      variantId: z.string().nullable(),             // approved wording id, or null
      choice: z.enum(["variant", "canonical", "rewrite"]),
      what: z.string(),                             // empty when the line is unchanged
      why: z.string(),                              // empty when unchanged; one specific sentence otherwise
      requirementIds: z.array(z.string()),
    })),
  })),
  skills: z.array(z.object({
    category: z.string().nullable(),
    refs: z.array(z.string()),                        // ["S1","S3"] — refs, not names
  })),
  requirementMatches: z.array(z.object({
    requirementId: z.string(),                        // "r1"
    verdict: z.enum(["met", "partial", "missing"]),
    evidenceRefs: z.array(z.string()),
    note: z.string(),
  })),
  plan: z.object({
    hiringFor: z.string(),                            // what this employer is hiring the person to do
    positioning: z.string(),                          // strongest defensible positioning
    narrative: z.string(),                            // one sentence, library facts only
    priorities: z.array(z.string()),                  // up to 4 requirement phrases
    qualifications: z.array(z.object({
      requirementId: z.string(),
      weight: z.enum(["mandatory", "differentiating", "secondary"]),
    })),
    evidence: z.array(z.object({
      ref: z.string(),                                // heading entry
      use: z.enum(["lead", "support", "omit"]),
      bullets: z.number(),                            // lines that entry should keep
      because: z.string(),                            // why it outranks or loses to another entry
    })),
    gaps: z.array(z.string()),                        // unmet requirements; a bare id is stored as the requirement text
    closeCall: z.boolean(),                           // true only when an omit could replace a lead
  }),
})
```

The bullet `text` is the wording on the resume. The user does not accept it line by line. `what` and `why` are kept only when the line differs from its source and the why names a real reason. Notes that only say "ATS", "impactful", "stronger keywords", or "better aligned" are dropped. `plan` is the strategy for this job: what the employer is hiring for, which entries lead, support, or stay off, and how many lines each one should have. It is stored on the resume. The overview names the included entries the strategy marked as the emphasis. It does not display `plan.narrative`. The strategy can overstate; the guard still checks every claim that is printed. The resume workspace overview is also built from the saved resume: which entries were selected, which bullets were rewritten, kept, or left off, and notes that still name a real reason. A requirement is named only when its id is on the job analysis and on a rewritten bullet. The overview does not repeat the match panel.

### Repair pass

After the guard, a rewrite reverted by G4, G13, or G16 can be tried once. The second call sees only those bullets (at most six), the source text, and the rejected wording. It uses the same TAILOR model and does not take a second tailored-resume credit. A repaired line is kept only when the guard accepts it. A failed repair leaves the first guarded resume. There is no further loop.

### Revision pass

After repair, `revisionRoute` decides whether another call is warranted. A draft with no strategy uses `revisionTargets`. A must-have requirement with direct bullet evidence that is not written on the resume, the strongest hands-on entry left at one line while several implementation bullets are unused, or a selected line that is vague or drops two or more job-relevant terms its own sources state, is a gap. Academic or skill-only evidence is not a gap. A specific line is not a gap. No gap means no extra call. That call rewrites only those entries (at most three, and at most six unused sources). It can add an entry the draft omitted.

A draft that returned a strategy takes a different call when the draft leaves a lead off, gives a lead fewer lines than the strategy asked while unused sources remain, lets a support entry crowd the lead, marks the ranking a close call, or still has one of those gaps. That call sees the strategy, the draft, and a bounded set of library excerpts. It may change which entries appear, how many lines each one has, their order, the summary, and the wording. The strategy is not assumed to be right. The result is kept only when the guard accepts every line and the revert count does not rise. If that pass leaves the draft unchanged and direct evidence is still off the page, the narrower entry revision still runs. A failed or invented revision leaves the guarded draft. There is no further loop. Repair and revision set `countsTowardQuota: false`, so they do not use a second tailored-resume allowance.

### System prompt (draft)

```
You tailor resumes. You are given a candidate's complete library of experience (each item has
a ref like E1, E1.B2, S4), a job posting, and its extracted requirements. Produce the strongest
honest resume for this posting.

TRUTHFULNESS — these rules override everything else:
1. Use only facts that appear in the library. Never add employers, titles, dates, tools,
   technologies, certifications, metrics, team sizes, scope or outcomes that the cited source
   bullets do not state.
2. Every bullet cites one or more sourceRefs from the entry it is listed under (E3.B1 only
   under E3). Up to five. Facts from those sources may be written as one sentence. A source
   from another role is not allowed. Records that are the same role may be cited together. Do not repeat a source already combined into another line.
3. Do not introduce any number that is not in the cited source. The summary may use a whole-year
   tenure taken from an entry's dates only when that figure is rounded down.
4. You may: rephrase for clarity, relevance, and order; drop words that do not help; lead with
   the fact most relevant to this posting; and use the posting's terminology ONLY when the cited
   source says the same thing ("Postgres" → "PostgreSQL" is fine; "SQL" → "PostgreSQL" is not;
   "Excel" may be written "Microsoft Excel"). Do not raise the role: helped, assisted, or
   supported does not become led, directed, or managed. Do not turn "used SQL" into a database
   the source does not name. Familiarity, use, coursework, a project, and professional
   experience stay in the category the cited sources state.
5. If the candidate lacks something the posting wants, leave it out. Do not imply it, and do
   not give them the job's title.
6. Do not describe academic, personal, or coursework use of a tool as production experience.

OBJECTIVE
Produce a finished resume. The bullet text is the wording on the page, not a suggestion to accept.
Rewrite when clearer wording stays inside the cited bullet. Leave a bullet unchanged when the
original is already stronger. Do not change a line only to swap a synonym.

The model also fills `plan` before the bullets: what the employer is hiring for, the defensible
positioning, which entries lead, support, or stay off and how many lines each should have, the
priorities, and the requirement ids it will not claim. The running prompt is `src/lib/ai/prompts/tailor.ts`.

REWRITING
- Keep every tool, metric, and outcome inside the cited bullet.
- "Merge and transform data" may become "Consolidated and transformed data".
- Spreadsheet joins may be rephrased. They may not become ETL, pipelines, or production engineering.
- Do not invent help-desk, customer-support, or on-call work from a nearby task.
- `what` names the editorial change. `why` names the requirement. Both are empty when the line is unchanged.

SELECTION
- Read the whole library, including projects. Prefer relevant, recent, specific evidence.
  A recent production project outweighs an older academic project when both relate to the role.
  Omit weak or redundant material.
- Always include EDUCATION entries (bullets optional).
- Fit the page length in the options. The length is a ceiling. Stop when another entry would not make the application stronger. Do not add lines to fill a second page.
- One page is not a quota of 10–14 bullets, and two pages is not a quota of 16–22. `composeResume` drops the lowest-value line when a render or a safety ceiling is over, and it may drop a one-bullet entry when that entry is the weaker one.
- Order bullets within an entry by relevance to the posting.
- Skills: choose relevant skill refs, grouped into 2–4 categories, most relevant first.

STYLE
- Bullets start with a strong verb, past tense (present tense for a current role), no first
  person, no filler, ideally under 30 words, plain text only (no emojis or special symbols).
- Summary: 2–3 sentences, third-person-implied ("Data analyst with…"), grounded only in the
  library, aimed at this role. Do not open with the posting's title unless a library headline
  or job title uses it. No clichés ("results-driven", "passionate", "team player").
  Prefer omitting years. If you mention years in a role or a career, use whole years only
  (round down; 2 years 7 months is 2, never 3) and only for the entry those dates belong to.
  Do not say the candidate worked with, for, or alongside a team, squad, or stakeholder unless
  a source bullet states that relationship. "Used by N squads" is not "worked with those squads."

MATCH REPORT
- Exactly one requirementMatches item per requirement id.
- "met": the cited evidence shows the requirement itself, not a nearby keyword. Five years of
  production ETL is not met by Excel joins. "partial": related or transferable evidence.
  "missing": no sufficient evidence. "missing" is a useful answer.
- evidenceRefs: the refs that support the verdict ([] for missing). note: one short sentence.
```

The emphasis option is passed as data inside `<options>`. The system prompt's truthfulness rules take priority over anything written in it.

## The fabrication guard (`features/tailor/validate.ts`)

Deterministic checks on `TailorOutput` **before** anything is saved. Pure function, so it gets thorough unit tests (`tests/unit/tailor-validate.test.ts`).

```ts
validateTailorOutput(output: TailorOutput, snapshot: LibrarySnapshot, analysis: JobAnalysis)
  → { output: TailorOutput /* cleaned */, reverts: number, issues: GuardIssue[] }
```

| # | Check | Action |
|---|---|---|
| G1 | `entries[].ref` not in snapshot | Drop the entry |
| G2 | Duplicate entry ref | Keep the first occurrence |
| G3 | Bullet `sourceRefs` that don't exist or belong to another role | Remove those refs. If none remain, drop the bullet. |
| G4 | Bullet text contains a number not present in its sources (normalise: strip commas/spaces; compare tokens matching `\d+(\.\d+)?%?` and `$`-amounts) | **Revert** to the first source bullet's original text; `reverted = true` |
| G5 | Bullet text empty or > 400 characters | Revert |
| G6 | Two bullets with identical `sourceRefs` | Keep the first |
| G7 | Skill refs not in snapshot | Drop them; drop empty categories |
| G8 | `requirementId` not in analysis | Drop that match |
| G9 | Requirement with no match | Add `{ verdict: "unassessed", evidenceRefs: [], note: "Not assessed." }` |
| G10 | `evidenceRefs` not in snapshot | Remove. If the verdict is met/partial and no evidence remains → `missing` |
| G11 | EDUCATION entry in snapshot but not in output | Append it (no bullets) |
| G12 | Tailored summary: an "N years" / tenure claim exceeds the whole years computed from snapshot dates (round down), a number is not in the library and is not that computed tenure, or a sentence names a tool, proficiency, responsibility, or result the library does not support. A skill name allows the name, not professional or project experience. Claims may come from different roles when each one is supported. | Drop the failing sentence. If none remain, use the library default summary (or empty). Count one revert. |
| G13 | Rewritten bullet names a tool, credential, overclaim (`production`, `ETL`, `pipeline`, `expert`, `senior`, and the same class), a deployment the source does not positively state (`not deployed` does not support `deployed`), or an invented kind of work (`help desk`, `customer support`, `on-call`) that the cited bullets do not support, allowing Excel/Microsoft Excel and Postgres/PostgreSQL | Revert to the first source bullet. Count one revert. |
| G14 | A later bullet repeats an earlier one (Jaccard ≥ 0.75 on content words, both at least 4 words) | Drop the later bullet. It returns as an excluded library bullet. Not a revert. |
| G15 | Verdict is `met`, but the requirement asks for years, production experience, ETL, help desk, customer support, or on-call work that the cited evidence does not show, or it names a known tool the cited evidence does not show | Downgrade to `partial`. Not a revert. The score uses this verdict. |
| G16 | The rewrite raises the role or the tool past the cited bullet. "Helped coordinate" does not become "Led". "Used SQL" does not become "Developed PostgreSQL infrastructure". Familiarity, having used a tool, coursework, building a project with it, and professional experience are not interchangeable. "Used Java" does not become coursework, a Java project, or professional Java experience. | Revert to the source bullet. Count one revert. |
| G17 | A bullet cites more than five sources | Drop it. Not a revert. Each source returns as its own library bullet. |
| G19 | A single source is already cited by a combined bullet | Drop the single line. Not a revert. |
| G20 | Verdict is `met`, but the only evidence is a skill and the requirement asks for experience or depth | Downgrade to `partial`. Not a revert. |
| G18 | Two education entries are the same degree (same institution and credential; end years within one year, or either year missing) | Keep the richer selected row. Drop the other. Not a revert. A distinct omitted degree is still appended by G11. |

All guard reverts are counted in `TailoredResume.guardReverts` (G4 + G5 + G12 + G13 + G16) and returned as `issues` for logging (codes only, no text). G14, G15, G17, G18, G19, and G20 are issues and do not increment `guardReverts`. A combined bullet that fails G4, G5, G13, or G16 is replaced by its source lines, and that counts as one revert.

> The guard catches the mechanical lies (fake numbers, rounded-up tenure in the summary, wrong-entry citations, invented skills). It can't catch a rephrasing that subtly overstates. That's what the "show source" popover in the editor and the evals are for.

Cleaned bullets include `reverted`. The model output does not.

Resolved rules:

- Checks run in the order above. The input is left unchanged.
- `reverts` counts bullets restored by G4 or G5, plus one if G12 changed the summary. A bullet with both a new number and empty or over-long text is restored once, as G4.
- `issues` are `{ code, ref }` only. The ref is an entry ref, bullet ref, skill ref, requirement id, or `"summary"`.
- A source ref is kept when it is a bullet on that entry, or on another library record of the same role. A repeated ref on one bullet is kept once, in first-seen order. Facts from a different role are not cited together.
- G4 reads `$` amounts and numbers, including thousands grouped with commas or spaces (`1,000`, `1 000`) and a trailing `%` (`20%`, `20 %`). Commas and spaces inside the token are removed before comparison. `$50` and `50` are different. `20%` and `20` are different. `2.5` and `2.50` are different. A `+` after a number is not part of the token.
- Restored text is the original text of the first remaining source ref.
- G5 treats whitespace-only text as empty. Length is the raw character count. 400 is kept. 401 is restored.
- G6 treats source refs as a set. Order does not matter. The kept bullet is the first.
- A second match for the same requirement id is dropped and logged as G8.
- Evidence refs may be an entry ref, a bullet ref, or a skill ref. A met or partial verdict with none left becomes missing. The note stays. A missing verdict stays missing. When the model sent no evidence refs at all, the issue ref is the requirement id.
- Omitted education entries are appended in snapshot order with no bullets, except a second record of a degree already kept. Other omitted kinds are not appended here. G18 drops that duplicate. The keeper is the selected row that has bullets, otherwise the richer library row. The same institution and credential match: `B.C.S. Honours` at Carleton and `Bachelor of Computer Science` at Carleton University are one degree. A bachelor and a master are not. End years more than a year apart stay separate.
- G12 runs after the entry, skill, and match checks. Tenure is whole years from snapshot dates, rounded down (year-only start is January, year-only end is December; a current role ends at `takenAt`). An "N years" / "N-year" / "N at {org}" claim, including spelled-out counts through twenty, must be ≤ the years at that organization when an employer is named, otherwise ≤ total EXPERIENCE years. Education phrases ("four-year degree") compare to EDUCATION dates instead. Digit numbers in the summary must appear in the library (headline, default summary, titles, organizations, locations, dates, bullets, skill names) or equal a computed whole-year tenure. A sentence is also dropped when it names a tool the library does not, raises a tool into a proficiency category the bullets do not state, or claims a responsibility the bullets do not state. Familiarity, use, coursework, a project, and professional experience stay distinct. A listed skill supports the name only. A sentence may draw on more than one role when each claim is supported. G12 issues use ref `"summary"`. The library default summary is source text and is not re-checked.

## Composing the resume (`features/tailor/compose.ts`)

`composeResume({ output, snapshot, analysis, length })` runs after the guard, the repair pass, and a revision when one was needed, before assemble. It does not call the model and does not invent employers, tools, dates, or metrics. Bullets it pulls in use the library text.

It writes three optional fields on `ResumeContent` (older resumes omit them):

- `sectionOrder`: entry sections for this resume. Experience stays first unless the strongest hands-on project clearly outranks the strongest included role. A line that names a known tool and is not generic or coursework counts as hands-on, so GIS practice is not ignored because it does not say Built. Coursework in the entry title is academic and does not outrank an internship or a project. Employment inside Experience stays chronological: a current role, then later end dates.
- `contacts`: verified profile links that belong on the resume. GitHub, LinkedIn, and portfolio links are kept. The same URL is kept once. A course link (Coursera and the same class of host) is left off, with a reason. A project URL is added only when the profile has no link of that kind and the entry is included.
- `review`: one note per library entry (`model_selected`, `prioritized`, `not_selected`, `lower_relevance`, `same_degree`, `same_role`, `covered`, `page_budget`, `no_marginal_value`, `overlapping_claim`, or `missing_source`), plus warnings. `overlapping_claim` means a thinner line on the same role was left off in favour of a more specific line. The library still has both. `same_role` means the facts are used on the other record of that role. `covered` means a project repeated evidence already on the page. `page_budget` means a line was left off to fit the chosen length. `no_marginal_value` means a plan did not ask for the entry and it showed none of the requirements. `fact_conflict` and `unresolved_dates` mean two records disagree and the resume did not pick a value. `within_ceiling` means a two-page allowance was not filled. `CURRENT_ROLE_OMITTED` is a warning when a current role with a title, employer, or bullet was not selected. It does not force the role onto the page. `missing_source` is an empty record, not a selection judgment.
- `headline` and `pageLimit`: the line under the name for this version, and the page ceiling. Omitted on older resumes.
- Display fields on an entry (`displayTitle`, `displayOrganization`, `displayStart`, `displayEnd`, `displayCurrent`): how this version prints a library row. Omitted on older resumes, which keep using the snapshot.

Other decisions, each with a ref and a short reason:

- Bullets on the same role that make the same claim are not treated as equal. The more specific supported line is kept on the resume when it is at least as relevant. A number by itself does not win. A thinner line stays when its library text is the only evidence for a requirement. A requirement word added only in the draft does not keep that thinner source. A combined line is split when one cited source has a more specific supported claim. The library bullet is not deleted or rewritten.
- When the model returned an evidence strategy, composition follows it. An entry marked omit is left off. A selected entry keeps at most the line count the strategy gave it, and unused library lines from that role are added when the draft wrote fewer than that count. Projects stay in the strategy's order. The Projects section leads only when the first lead is a project. Keyword ranking does not replace a lead, and a role is not capped because of its title. When the page estimate is over, a lower-weighted extra project is removed before a lead loses a line. Page measurement can still turn a line off so the rendered resume fits the chosen length. A draft with no strategy keeps the earlier checks: a hands-on project the model left out is included when it is the strongest project for the posting, or when it adds a must-have the selected resume does not already show. A second project that only repeats that evidence is left off. On two pages, a project can also stay when it adds a posting keyword the page does not already show. An omitted role is included the same way, up to two. Records of one role are one heading. The same employer, a compatible title, and the same or overlapping dates are required. A level change such as intern and senior stays separate, and so do two titles that do not share the role. Missing dates stay separate. "Def Hacks" and "Defhacks.co" count as one employer. The heading keeps the richer record's title and dates. Bullets may cite either record, and a fact that only the other record states can be added under that heading when it adds a posting term, a number, or a tool the selected lines do not already state. Equivalent lines are kept once. The library rows are not merged or deleted. Two jobs at the same employer in different years both stay. Without a strategy, a shipped project outranks a project whose overlap is a shared keyword, and on one page a role that matches the posting less keeps two bullets so the closer role keeps its evidence. Academic or unfinished wording does not count as hands-on, and it does not count as deployed. Selected lines are then trimmed only when they pass a safety ceiling (14 bullets on one page, 22 on two) or the line estimate of the page. That ceiling is not a target. A two-page choice may stay well under it. The lowest-weight entry can lose its only bullet before a lead loses a line. After assembly, the classic resume is rendered at the regular font. Included lines are turned off until that render fits the chosen length, including a one-bullet entry when it is the weaker one. A line that still will not fit stays off, with a review note, rather than by shrinking the font. Employer identity treats an acronym of the longer name as the same employer. Overlapping dates with a compatible title are one stint. A missing date does not merge. A dated gap stays two jobs unless a confirmation names both records. Conflicting dates or titles are stored on the resume as unresolved and are not filled in from whichever row was read first. A confirmation may supply the title and dates for that stint. The library rows are not merged or deleted. A project whose title is a list of roles is shown under the project name on this resume only. `headline` is the job-specific line under the name, or null. Older resumes omit it and still show the profile headline. `pageLimit` records the ceiling.
- A non-current role with weak, generic evidence is left off when a hands-on project is clearly stronger. The reason is `lower_relevance`.
- A generic bullet is replaced by a stronger library bullet from the same entry when the gap is clear. The wording is the library sentence.
- A skill the posting names is added when a hands-on bullet states it. A skill that appears only on a course or education line is recorded as `academic` and is not added. A name with no bullet is `name_only` and is not added. A skill stored as coursework is `academic` unless a bullet shows the work outside a course. A skill stored as basic stays `name_only` unless a bullet shows the work. The printed name keeps the level.

The editor, PDF, DOCX, and plain text use `sectionOrder` and `contacts` when those fields are present. A save keeps the stored order, contacts, and review.

## Assembling the editable resume (`features/tailor/assemble.ts`)

`assembleResumeContent(validated, snapshot, createId?, notes?, composition?) → ResumeContent`:
1. Selected entries first, in the order `composeResume` already set within each kind (kinds follow `composition.sectionOrder` when it is passed, otherwise Experience, Projects, Education, Certifications, Volunteer, Other). `contacts` and `review` are stored when composition passed them.
2. Each selected bullet cites one to five sources from that entry. The content bullet is `{ id: nanoid(), text, included: true, sourceRefs, sourceIds, reverted, edited: false, originalText, suggestion, suggestionNote, changeWhat, requirementIds }`. `text` is already the tailored wording. `sourceIds` are the stable library bullet ids. `originalText` is the cited source text, joined when the line uses more than one. Restoring that line replaces it with one bullet per source, in library order, using each source's wording. PDF and DOCX read those bullets. `suggestion` keeps the tailored wording when it differs and was not reverted, so the user can restore it after switching back. `suggestionNote` is the specific reason, and `changeWhat` is what the edit changed. A vague reason is stored as null. `requirementIds` are the requirement ids that motivated the change. The library itself is not changed. A later tailor copies wording the user edited (`edited: true`) onto the same source ids. If both copies have an `originalText` and those texts differ, the old edit is left off. Older resumes without `sourceIds` still match on the entry ref plus source refs. Older resumes without `changeWhat` read it as null.
3. **Unselected library content is included too, switched off:** every snapshot entry not chosen → `included: false` with its original bullets (`included: false`). Every unselected bullet of a chosen entry → appended with `included: false`. This is what lets the user toggle things back in.
4. Summary: `{ text: validated.summary, included: true }`.
5. Skills from refs → names, grouped by the AI's categories.

`assembleResumeContent(validated, snapshot, createId?)`. `createId` defaults to `nanoid`. Tests pass a counter.

Resolved rules:

- Inside a kind, selected entries stay in the order they were passed in. `composeResume` sets that order: employment is chronological, and projects are ranked by relevance. Snapshot entries left out follow them, in snapshot order, `included: false`, with their original bullets off.
- A bullet the model cited is not also appended as an off copy. An education entry the guard appended with no bullets gets its original bullets back, switched off.
- The summary is included. Text past 800 characters is cut to 800. Bullet text past 400 characters is cut to 400.
- A skill ref repeated in one category is listed once. A ref that is not on the snapshot is skipped.
- The content stores refs and kinds. Titles, employers, and dates stay on the snapshot.

## Scoring (`features/tailor/score.ts`)

Deterministic and explainable:

```
weight: must = 2, nice = 1        value: met = 1, partial = 0.5, missing = 0
score = round(100 × Σ(weight × value) / Σ(weight))      (null if no requirements)
```

`unassessed` is omitted from both sums. The score is null when the posting has no requirements, and when every requirement is unassessed.

Shown as **Match score**, with the per-requirement breakdown. The score reflects the library, not the resume's wording, so re-tailoring won't game it. "How this is scored" says it is not a hiring probability, and that requirement wording varies.

`scoreMatch(analysis, matches) → MatchReport`. `score` is `null` when there are no requirements (`MatchReport.score` is nullable).

Resolved rules:

- `round` is `Math.round`. A value of 12.5 becomes 13. One met must and one missing nice-to-have is `round(200 / 3) = 67`.
- Verdicts follow the analysis order. The first match for a requirement id wins. A requirement with no match is unassessed, with the note "Not assessed.", and is left out of the score. An older missing row with that same note is read as unassessed. The stored score is not rewritten on read.
- A note past 200 characters is cut to 200.

## Requirement states (`features/tailor/requirement-state.ts`)

The match panel does not show the stored verdict. `requirementState` recomputes one state from the resume on screen. The labels are **Met**, **Not on this resume**, **Needs review**, and **Not demonstrated**. The first match wins:

1. **Met** (state `in_resume`). The stored verdict is `met`, and an evidence ref points at included content or a key term appears in included text. A keyword alone does not do this when the verdict is partial or missing.
2. **Not on this resume** (state `in_library`). That evidence exists only on excluded content. This is a resume gap: Include turns those bullets, entries, and skills on in the resume already open. No new tailor, and no quota. Rewriting is not offered.
3. **Needs review.** The verdict is partial or unassessed, or a related term is already on the resume without a `met` verdict. Related experience does not fully demonstrate the requirement.
4. **Not demonstrated** (state `no_evidence`). Nothing in the library supports it. Add to library is the action. Rewriting the resume is not offered, and the hint says so.

Excel and Microsoft Excel, and Postgres and PostgreSQL, are the same term. Java is not JavaScript.

A key term is a library skill name, or a job keyword, that appears in the requirement text. Matching uses the keyword-coverage rules, so Java does not match JavaScript. A term in included text wins over the same term on excluded content. Excluded text is the resume line that is switched off, and the library original when that line is off. Add to library stays on **Not demonstrated** only.

The stored score does not change while you edit.

## Keyword coverage (`features/tailor/keywords.ts`, client + server)

`keywordCoverage(content, snapshot, keywords) → { covered: string[], missing: string[], pct: number }`
- Text = plain-text render of **included** content (summary + entry titles/orgs + bullets + skills).
- Normalise: lowercase; keep `+ # .` (C++, C#, .NET); collapse whitespace.
- A keyword matches if it, or a listed alias, appears as a whole word or phrase (word-boundary regex with escaped keyword). Aliases include Excel/Microsoft Excel and Postgres/PostgreSQL. A covered keyword is not a met requirement.
- Recomputed on every edit in the resume workspace. Not stored.

Resolved rules:

- The searched text is the included summary, the title and organization of each included entry, included bullets on those entries, and skill names. Dates, locations, and contact details are left out.
- `+`, `#`, and `.` are part of the word. `Java` does not match `JavaScript`, `C++` matches `C++`, and `.NET` does not match inside `ASP.NET`.
- `covered` and `missing` keep the keyword list's spelling and order. `pct` is the rounded share of keywords covered. An empty keyword list yields `0`. A blank keyword is missing.

`resumePlainText(content, snapshot) → string`. This is the Copy text string. It is the same lines as the PDF and DOCX (`resumePdfLines`), joined with newlines. Included content only. No RoleRefine branding. Section order follows the resume when it has one, otherwise Summary, Experience, Projects, Education, Certifications, Volunteer, Other, Skills. Header links follow the resume's selected contacts when those were stored.

- Dates use the resume date format (`Nov 2023 – Present`). A current role with no start prints `Present`. A missing date is left out. A start and end that format to the same label are printed once, so a project dated only 2025 does not read “2025 – 2025”.

## 4. COVER_LETTER — library + job + your reasons → letter (1.0)

### System prompt (draft)

```
You write cover letters grounded strictly in the candidate's library.

TRUTHFULNESS (overrides everything):
- Claims about the candidate must come from the cited library refs. Never add employers,
  titles, tools, metrics, or outcomes that are not in those items. No new numbers.
- Claims about the company or role must come from the posting ("POSTING") or the candidate's own
  reasons ("WHY"). Never invent company facts, values, products, news or culture.

STRUCTURE: 3–5 paragraphs: (1) the role and a one-line hook connecting the candidate's strongest
relevant experience to the role; (2–3) two or three requirements from the posting matched to
```

### Guard (`features/letters/validate.ts`)
- L1: Unknown refs (not in the snapshot and not `POSTING`/`WHY`) → removed. A paragraph left with no refs is kept only if it's the opening or closing paragraph.
- L2: Number check per **sentence**: every number must appear in the cited library sources, the posting, or the WHY text; otherwise **drop that sentence** and mark the paragraph `reverted: true` (counted in `guardReverts`).
- L3: `WHY` cited but no WHY text provided → remove the `WHY` ref; if the paragraph is about motivation and has no other source, keep it but flag it in the UI ("Add your own reasons to strengthen this").
- L4: `requirementIdsAddressed` filtered to real ids.
- Greeting: `Dear {recipientName or "Hiring Manager"},`. Closing from the model (or `Sincerely,`), and the signature from the profile (never from the model).

Resolved rules:

- A ref is known when it is on the snapshot, or it is exactly `POSTING` or `WHY`. Other refs are removed. Duplicates are removed. A paragraph left with no refs stays when it is the first or the last paragraph. One paragraph is both, so it stays. A middle paragraph with no refs is removed. A blank paragraph is removed.
- A sentence ends at `.`, `!`, or `?` when whitespace or the end follows. A period between digits stays inside the number (`3.14`). `Mr`, `Mrs`, `Ms`, `Dr`, `Prof`, `Sr`, `Jr`, `St`, `e.g`, and `i.e` do not end a sentence. A period after a digit still ends a sentence when whitespace follows (`14. Next`).
- L2 uses the same number tokens as G4. `$50` and `50` differ. `20%` and `20` differ. `1,000` matches `1000`. A bullet ref is checked against that bullet's text. A skill ref is checked against the skill name. An entry ref is checked against the title, organization, location, dates, and that entry's bullet text. `POSTING` uses the posting slice the model saw (12,000 characters). `WHY` uses the trimmed note. A blank note counts as none.
- One dropped sentence marks the paragraph reverted and counts once. Two dropped sentences in the same paragraph still count once. When no sentence remains, the paragraph is removed and the revert still counts. L1, L3, and L4 are issues only.
- "About motivation" means the paragraph cited `WHY` and no other ref remains. That paragraph is kept, including in the middle, with `needsWhy: true`. The workspace line is "Add your own reasons to strengthen this". Other refs stay, with no flag.
- The closing line is not number-checked. A blank closing becomes `Sincerely,`. A longer closing is clipped to 60 characters. The greeting ignores the model string. An empty recipient name becomes Hiring Manager. The signature is the profile name, or empty when the profile has no name. Paragraphs are clipped to 1,200 characters. The guard does not cap the letter at 5 paragraphs.
- Issues carry a code and a ref (`p0` for a paragraph, the unknown ref, or the requirement id). They never carry paragraph text, posting text, or WHY notes.

Then `assembleLetterContent()` → `CoverLetterContent` (all paragraphs `included: true`, plus the filtered requirement ids).

## Library wording (current)

Rewrite, Strengthen, and headline or summary suggestions use `BULLET_COACH` and Haiku. They do not add a meter. Free is 10 and Pro is 300 per month, from `plans.ts`.

A failed model call sets `AiCall.success` to false and does not consume the allowance. A call that returns and is then dropped by the guard still counts, because success is recorded when the model responds.

**Rewrite** (`prompts/rewrite.ts`) takes one bullet and a capped library context. The output is one `text`, one `why`, and an optional `question`. `reviewRewrite` drops an empty line, an unchanged line, a new number, an unsupported claim, or a raised role. A question that would add a number is discarded. Accept replaces `Bullet.text` and stores the previous text as a canonical variant and the new text as an approved rewrite. Undo within 8 seconds deletes that rewrite only while the bullet still has the accepted text.

**Strengthen / Explore experience** (`prompts/strengthen.ts`) first asks questions about the tool or method, the scope, the deliverable, a measurable outcome, and the technical detail, and only where the saved lines do not already say it. A question must contain `?`, must not start by asserting the fact, and must not add a number. After the person answers, a second call drafts one bullet. A confirmed yes is turned into affirmative evidence (`formatConfirmedAnswer`); any detail they type is authoritative. If follow-up questions appear, earlier confirmations are kept and merged into the draft call. Saving adds a new bullet. It does not overwrite the thin original. The library shows this as **Find missing details** on the experience footer.

**Overlap hints** are local only (`features/library/overlap.ts`). They compare content tokens within one experience and never call the model on page load. They never delete or merge bullets.

**Headline and summary** (`prompts/wording.ts`) suggest up to four lines. A new request replaces unapproved suggestions and leaves approved wording in place. A headline is the short focus under the name: at most eight words, no vertical bars, and it does not start with an action verb. "Built and deployed a production web app" is a bullet, not a headline. `headlineShapeAllowed` drops that shape, a repeated past job title, and a tool list. `headlineRankAllowed` rejects a rank the library does not already use, and a headline never writes `Entry.title`. Approving one closes the list and sets it as the default. `reusableSummaryAllowed` rejects a classification code such as CS-01 unless that code is an entry title. A summary saved for one job keeps `jobId` and does not change `User.summary`.

Approved bullet variants are listed in the tailor user message under `<variants>`. `preferSavedWording` forces a canonical choice back to the snapshot text and a variant choice to the exact approved text when that variant belongs to the cited bullet. The fabrication guard then runs on that text. The match score still comes only from requirement verdicts.

## 7. BULLET_COACH — three suggestions with placeholders (1.1)

The call above is the one grounded rewrite. The later coach still returns three suggestions and uses a bracketed placeholder when a metric is missing. That UI is not this rewrite.

**Input:** one bullet, its entry (title, org, dates), the user's skills list, and the current strength checks that fail.

**Output (`CoachOutput`):**
```ts
z.object({
  suggestions: z.array(z.object({ text: z.string(), why: z.string() })),  // 3
  questions: z.array(z.string()),   // facts to ask the user, e.g. "Roughly how many reports did you automate?"
})
```

**Prompt rules:** rewrite using only facts in the original bullet; where a metric would help, insert a **bracketed placeholder** (`[X%]`, `[number] users`, `[time saved]`) instead of a number; start with a strong verb; under 30 words.

**Guard:** drop any suggestion containing a number (outside `[...]`) that isn't in the original. **UI rule:** a suggestion with placeholders can be applied, but it can't be saved until every `[...]` is replaced by the user.

## Deterministic helpers (no AI)

### Bullet strength → strength (`features/library/strength.ts`)

`bulletStrength(text, skills, role?) → { score: 0–6, tier, passed: CheckId[], fixes: string[], concerns, example: string | null }`

`role` defaults to `accomplishment`, which is what the free tool and the reviewed tiers use. `record` is used for education, certification, and a line that says coursework. A record is not scored on the verb or metric checks, so a coursework line is not called weak for lacking a number and is not called an accomplishment. `concerns` separates missing information, writing clarity, and evidence. A verb that already appears later in the line asks to start with that verb. It does not ask to add an action verb.

| Check | Pass condition |
|---|---|
| `verb` | First word is in the strong action-verb list (`verbs.ts`, past and present, including Completed, Coordinated, Resolved, Processed, Reconciled, Maintained, Supported, and Prepared); fails on "Responsible", "Helped", "Worked", "Assisted", "Tasked" |
| `metric` | Contains a digit, %, $, or a multiplier ("2x") |
| `length` | 8–32 words |
| `voice` | No first-person pronouns (I, me, my, we, our) |
| `filler` | None of: "responsible for", "duties included", "various", "etc", "helped with", "tasked with", "worked on" |
| `specific` | Mentions one of the user's skills or a known tool/domain term |

Tier: 0–2 **Weak** · 3 **Fair** · 4 **Good** · 5 **Strong** · 6 **Excellent**. Used by the strength meters, the library card’s separate bullet-strength summary (Strong or better is score 5 or 6), the free Bullet Strength Checker, and the resume workspace. Library completeness is the five checks on that card and is a different fact from this score. Table-driven unit tests (≥ 30 cases).

Resolved rules:

- `skills` is the user's skill names. A match is case-insensitive and must be a whole word or phrase, so `Java` does not match `JavaScript` and a one-letter skill matches only as its own word.
- `verbs.ts` includes past and present (`Led` and `Lead`) and both `-ize` and `-ise`, including operational verbs such as Completed, Coordinated, Resolved, Processed, Reconciled, Maintained, Supported, and Prepared. The first word is compared with surrounding punctuation removed. The check does not receive whether the role is current; present-tense verbs are in the list so those bullets can pass. Weak openers stay out.
- A metric is a digit, `%`, `$`, or a multiplier such as `2x` or `2 x`. A spelled-out figure (`two`, `twice`, `one client`) still fails the check. `one of`, `one-off`, `one-time`, and `one-on-one` are not figures. Words are split on whitespace; 8 and 32 both pass `length`.
- First person is `I`, `me`, `my`, `we`, `our`, including contractions (`I'm`, `I've`, `I'd`, `I'll`, `we're`, `we've`, `we'd`, `we'll`). `i.e.`, `your`, `image`, and `us` do not fail `voice`.
- Filler phrases match as whole words. The fix quotes the first phrase found, in the order listed above.
- `specific` also accepts `KNOWN_TERMS` in `strength.ts` (SQL, Excel, Python, React, AWS, WordPress, ArcGIS Pro, QGIS, ArcPy, PostGIS, FME, and the rest of that list).
- Each fix names the next tier: Weak → Fair, Fair → Good, Good → Strong, Strong → Excellent. Excellent has no fixes.
- A missing metric says "If you have a number for this, add it to reach {tier}." A spelled-out figure says "Write that figure as a digit to reach {tier}." Neither tells you to invent a number. A short bullet asks for one concrete detail only if there is more to say. A missing skill or tool asks you to name one only if it belongs in the line. A long bullet says to shorten it to 32 words or fewer.
- The meter draws 5 segments, one per tier. Weak fills 1 and Excellent fills 5. Hover and keyboard focus show a question, then the fixes. The question asks only about what the line does not already state: the tool or method, the deliverable, and a count, size, or time the person already has. It names words from the line and does not supply an answer. A line with no failing check has no question.
- `example` is the shape for the first failing check, from `strings.strength.examples`, or null when every check passes. It is not a rewrite of the bullet and does not add an employer, a tool, or a number the bullet did not have. A missing metric uses the placeholder “[a number you have]”. A spelled-out figure shows the same words with the figure as a digit (“twelve clients” becomes “12 clients”). The strength meter shows the fixes. The note on the example says to use numbers and tools you already have. The library card does not list those rows.

## Evals (`evals/`)

Run before merging any change to prompts, schemas, models, or effort.

- `evals/fixtures/libraries/*.json`: 4 fake personas as `LibrarySnapshot`s (new CS grad; BI/reporting analyst moving to dev; mid-level frontend dev; career changer from retail). Skips IMPORT so runs are cheap and repeatable.
- `evals/fixtures/postings/*.txt`: 6 real-style postings (junior dev, data analyst, frontend, government IT developer, support engineer, product-y role).
- `evals/fixtures/resumes/*`: 3 fake resumes (PDF/DOCX/text) for IMPORT runs. Reuse and expand v1's `backend/tests/static/` files. Those files are not in this repo, so the folder is still empty. `npm run evals` does not run IMPORT.
- `npm run evals` → for each library × posting: ANALYZE + TAILOR + guard + score. Even pair indexes in that sorted order also run COVER_LETTER (half the pairs). Those letters alternate a fixed WHY note and no WHY text, starting with the note. Resume focus is the included bullet refs from that pair's tailored resume when tailoring succeeded. Writes `evals/out/<timestamp>/<pair>.json` (gitignored) and prints a table:

  `pair | reverts | dropped bullets | match score | words | seconds | $cost`

  `reverts` is the guard's G4, G5, and G12 count. `dropped bullets` is how many model bullets are absent from the cleaned output. `words` is the plain-text word count. `seconds` is wall time for the pair. `$cost` is the sum of that pair's `AiCall` costs, including the letter when one was written. The run uses one page and no emphasis. Letters use tone professional and length standard. It does not create jobs, resumes, or letters. Calls are charged to `SEED_USER_ID` and count toward that account's quota. If remaining analyses, tailors, or cover letters are below the counts the run needs, the script exits before any model call.

  A second table lists the letter pairs: `pair | letter reverts | letter words`. `letter reverts` is the L2 count. Read 5 letters whose output has `letter.whyProvided: false`. Any invented company fact → fix the prompt before merging. Record that review in `evals/NOTES.md`.

- `npx tsx --conditions=react-server scripts/compare-tailor.ts` runs the full tailor path (generate, guard, one repair when needed, one revision when needed) on the saved Hootsuite library snapshot and on a reporting posting. It prints the resumes and the `AiCall` token counts. It does not save a resume. Those calls set `countsTowardQuota: false`, so they are not a second tailored-resume allowance. The eval table above does not print resume text. `LIVE_TAILOR=1 npx vitest run tests/unit/live-compare.test.ts` is the same run under the loader that can also count the rendered pages.

- **Manual rubric** (read 5 random pairs per run): (1) any claim not supported by its source? (2) were the most relevant items selected? (3) does it read like a strong human-written resume? (4) is the summary grounded?
- **Fail conditions:** any fabrication found manually → fix the prompt before merging. Average reverts per tailored resume > 0.5 → tighten the prompt.
