## `runStructured()` — the only way to call the AI

`src/lib/ai/run.ts`. Feature code never imports `@anthropic-ai/sdk` directly.

```ts
type RunArgs<S extends z.ZodTypeAny> = {
  kind: AiCallKind;                         // from the Prisma enum
  userId: string | null;                    // null ONLY for FREE_TOOL
  usedBonusCredit?: boolean;                // set by the caller from the quota check
  system: string;
  content: Anthropic.ContentBlockParam[];   // user message content blocks
  schema: S;
  refId?: string;                           // jobId / resumeId / coverLetterId / prepKitId
};

type RunResult<T> =
  | { ok: true; data: T }
  | { ok: false; code: "AI_FAILED" | "AI_REFUSED" | "AI_TRUNCATED" };

export async function runStructured<S extends z.ZodTypeAny>(args: RunArgs<S>): Promise<RunResult<z.infer<S>>>
```

Implementation requirements:
1. Look up `AI_TASKS[kind]`.
2. Call `client.messages.parse({ model, max_tokens, system, messages: [{ role: "user", content }], output_config: { format: zodOutputFormat(schema), effort } })`. Imports: `zodOutputFormat` from `@anthropic-ai/sdk/helpers/zod`. (If the helper rejects a Zod 4 schema, fall back to `jsonSchemaOutputFormat(z.toJSONSchema(schema))` from `@anthropic-ai/sdk/helpers/json-schema` and parse the result with Zod yourself.)
3. `stop_reason === "refusal"` → `AI_REFUSED`. `stop_reason === "max_tokens"` → `AI_TRUNCATED`. `parsed_output` null or a thrown error → `AI_FAILED`.
4. **Always** insert an `AiCall` row (success or not) with `model`, `inputTokens`, `outputTokens`, `cacheReadTokens`, `cacheWriteTokens` (from `usage`), `durationMs`, `costMicros`, `errorCode`, `refId`, `usedBonusCredit`. On success with `usedBonusCredit`, decrement the bonus credit in the same transaction (see `04-DATA-MODEL.md` → Quotas).
5. Client config: `timeout: 120_000`, `maxRetries: 2` (the SDK retries 429/5xx).
6. **Never log** prompt content, file content, or model output. Log `kind`, ids, codes, tokens, duration.

### Structured-output schema rules (API limits)

AI output schemas are **separate** from the stored/DB schemas and kept loose, because the API's JSON Schema support excludes `minLength`/`maxLength`, numeric min/max, and array sizes beyond `minItems` 0/1. Limits and cleanup are enforced **in code after** the call.

- Use only: `z.object`, `z.string()`, `z.boolean()`, `z.array()`, `z.enum()`, `.nullable()`.
- No `.min()`, `.max()`, `.url()`, `.regex()`, `.default()`, or recursion in AI schemas.
- Optional values: `.nullable()` (not `.optional()`), so every key is always present.

Each prompt module (`src/lib/ai/prompts/<kind>.ts`) exports `SYSTEM`, `buildContent(...)`, and `OutputSchema`.

## 1. IMPORT — resume → library

### Input
- **PDF:** send natively as a document block (no PDF parser needed; Claude reads text and layout):
  ```ts
  { type: "document", source: { type: "base64", media_type: "application/pdf", data: base64 } }
  ```
  followed by a text block: `"Extract this resume into the schema."`
- **DOCX:** `mammoth.extractRawText({ buffer })` → text block wrapped in `<resume>…</resume>`.
- **Pasted text:** text block wrapped in `<resume>…</resume>`.
- Reject text under 200 or over 40,000 characters, and files over 5 MB.

### Output schema (`ImportOutput`)

```ts
z.object({
  profile: z.object({
    fullName: z.string().nullable(),
    headline: z.string().nullable(),
    email: z.string().nullable(),
    phone: z.string().nullable(),
    location: z.string().nullable(),
    links: z.array(z.object({ label: z.string(), url: z.string() })),
    summary: z.string().nullable(),
  }),
  entries: z.array(z.object({
    kind: z.enum(["EXPERIENCE","PROJECT","EDUCATION","CERTIFICATION","VOLUNTEER","OTHER"]),
    title: z.string(),
    organization: z.string().nullable(),
    location: z.string().nullable(),
    startDate: z.string().nullable(),   // "YYYY-MM" | "YYYY" | null
    endDate: z.string().nullable(),
    isCurrent: z.boolean(),
    url: z.string().nullable(),
    bullets: z.array(z.string()),
  })),
  skills: z.array(z.object({ name: z.string(), category: z.string().nullable() })),
  warnings: z.array(z.string()),        // shown on the review screen
})
```

### System prompt (draft)

```
You extract resumes into structured data for a resume-tailoring app.

Rules:
- Copy text faithfully. Do not rewrite, improve, summarise or merge bullets. Only fix obvious
  extraction artifacts (broken hyphenation, stray bullet symbols, doubled spaces).
- Never invent information. If a field is not present, use null (or [] for lists).
- Dates: "YYYY-MM" when month and year are known, "YYYY" when only the year is known, otherwise null.
  "Present"/"Current" → endDate null and isCurrent true.
- kind: paid roles, internships and contract work → EXPERIENCE; personal/academic/open-source
  work → PROJECT; degrees/diplomas/courses → EDUCATION; certifications/licences → CERTIFICATION;
  unpaid community work → VOLUNTEER; anything else → OTHER.
- Every bullet belongs to exactly one entry, in original order. Paragraph-style descriptions
  become one bullet per sentence.
- Skills: include items from any skills section, plus technologies/tools explicitly named in
  bullets. One skill per item ("React", not "React/Redux" — split those). Use a short category
  ("Languages", "Frameworks", "Tools", "Cloud", "Data", "Soft skills") or null.
- profile.headline: the line under the name if present, else null. Do not create one.
- Add a warning for anything you could not place or were unsure about (e.g. "Dates for 'Acme'
  were unclear").
```

### Post-processing (code, `features/import/extract.ts`)

1. Trim all strings; drop empty bullets and entries with an empty title.
2. Dates not matching `^\d{4}(-(0[1-9]|1[0-2]))?$`, or outside 1900–2099, → null (add a warning). "Present", "Current", "Now", or "Ongoing" on the end date → `endDate` null and `isCurrent` true, with no warning. If `isCurrent` is true, clear `endDate`. If the end date is before the start, clear the end date and warn.
3. Skills: dedupe by `nameKey`; drop names over 50 characters.
4. Bullets over 400 characters → keep, and set `long: true` for the review screen. A bullet over 2,000 characters is cut to 2,000, still flagged, with a warning.
5. Links: keep only `http(s)://` URLs; prepend `https://` to bare domains. The same rule applies to an entry URL. Drop URLs still over 300 characters.
6. Clamp the rest to the library caps, and warn when something was shortened: profile name 80, headline 120, email 254, phone 40, location 80, summary 2,000, link label 40, entry title and organization 120, entry location 80, skill category 40. Keep at most 5 profile links.
7. Return to the client for review. **Nothing is saved until `commitImport`.** `extractResume` checks the IMPORT quota before the model call. A bad file is `VALIDATION` and does not use quota.

## 2. ANALYZE — posting → requirements

### Input
`<posting>{rawText truncated to 15,000 chars}</posting>`

### Output schema (`AnalyzeOutput`)
Same as `JobAnalysis` in `04-DATA-MODEL.md` but **without** `requirements[].id`. Code assigns `r1…rN`, caps requirements at 20 and keywords at 30, and dedupes keywords case-insensitively.

### System prompt (draft)

```
You analyse job postings for a resume-tailoring app. Extract only what the posting states.

- title, company, location: as written. If the company is not named, use "Unknown company".
- seniority: infer from title and years of experience; "unknown" if unclear.
- summary: 1–2 plain sentences describing the role.
- requirements: 5–20 distinct, concrete requirements. Split compound lines
  ("React and TypeScript" → two requirements). importance "must" for required/minimum
  qualifications, "nice" for preferred/asset/bonus. Skip generic filler ("team player",
  "fast-paced environment") unless it is the only requirement of its kind.
- keywords: 10–30 terms an applicant-tracking system would match: tools, technologies,
  methods, certifications, domain terms. Use the exact spelling from the posting.
- workMode, employmentType, salary (min/max/currency/period), referenceNumber
  (requisition / competition / selection process number): only if stated; otherwise
  UNKNOWN / null. Never estimate salary.
```

Post-processing: the analysis pre-fills `Job.workMode`, `employmentType`, `salary*`, `referenceNumber` only where the user hasn't already set them.

## 3. TAILOR — library + job → tailored resume

### Library serialization (`features/library/serialize.ts`)

Short refs instead of UUIDs: fewer tokens, and the model doesn't mangle them. `serializeLibrary()` returns `{ text, snapshot }`, where `snapshot` is the `LibrarySnapshot` (ref → DB id), stored on the Tailor. Example (illustrative content, not real data):

```
PROFILE
Name: Morgan Example | Headline: Data & reporting analyst
Default summary: …

E1 | EXPERIENCE | Junior Program Officer | Canada Revenue Agency | Ottawa, ON | 2023-11 – Present
  E1.B1: Built and maintained 14 IBM Cognos reports used by a 20-person processing team.
  E1.B2: Automated monthly business review workbook with Excel VBA, cutting prep time from 2 days to 3 hours.
E2 | PROJECT | Booking bot | — | — | 2025-03 – 2025-04
  E2.B1: Wrote a Python/Playwright bot that …
E3 | EDUCATION | B.CS. Honours | Carleton University | Ottawa, ON | – 2023
SKILLS
  S1: Python (Languages)
  S2: SQL (Languages)
  S3: IBM Cognos (Tools)
```

`serializeLibrary(library, takenAt)` is pure. The caller passes `takenAt` (stored on the snapshot); the function does not read the clock. The snapshot is the ref map the tailor pipeline stores.

The prompt text is one record per line. Email, phone, location, profile links, and entry URLs stay on the snapshot and are left out of the text. An empty name, headline, summary, title, organization, location, or date range is an em dash (`—`). A range with no start and an end date is `– 2023` (en dash). A current role is `{start} – Present`, or `Present` when the start is missing. Dates in the text are the stored `YYYY` or `YYYY-MM` strings. Newlines in a summary or bullet become one space in the text; the snapshot keeps the original string. A skill with no category has no parentheses. A `|` in user text is left as written. The `SKILLS` heading is always present.

Ordering: entries grouped by kind (EXPERIENCE, PROJECT, EDUCATION, CERTIFICATION, VOLUNTEER, OTHER). Inside a kind, current roles come first, then end date descending, then start date descending. A year with no month counts as December on an end date and January on a start date (`2024` is newer than an end of `2024-06`, and ties an end of `2024-12`). A missing or unparseable end date on a past role sorts after every dated end. Equal dates break by `sortOrder`, then id. Refs are assigned after that order: `E1`… across all entries, `E1.B1`… by bullet `sortOrder`, `S1`… by skill `sortOrder`.

### Input content (user message)

```
<library>
{serialized library}
</library>

<job>
Title: {title} | Company: {company} | Seniority: {seniority}
Requirements:
  r1 [must][skill] 3+ years of React
  r2 [nice][certification] AWS certification
  …
Keywords: React, TypeScript, AWS, CI/CD, …
</job>

<posting>
{rawText truncated to 12,000 chars}
</posting>

<options>
Target length: 1 page (about 450–600 words of content).
Emphasis from the candidate: {emphasis or "none"}
</options>
```

### Output schema (`TailorOutput`)

```ts
z.object({
  summary: z.string(),
  entries: z.array(z.object({
    ref: z.string(),                                  // "E1"
    bullets: z.array(z.object({
      sourceRefs: z.array(z.string()),                // ["E1.B2"] or ["E1.B1","E1.B3"]
      text: z.string(),
    })),
  })),
  skills: z.array(z.object({
    category: z.string().nullable(),
    refs: z.array(z.string()),                        // ["S1","S3"] — refs, not names
  })),
  requirementMatches: z.array(z.object({
    requirementId: z.string(),                        // "r1"
    verdict: z.enum(["met", "partial", "missing"]),
    evidenceRefs: z.array(z.string()),
    note: z.string(),
  })),
})
```

### System prompt (draft)

```
You tailor resumes. You are given a candidate's complete library of experience (each item has
a ref like E1, E1.B2, S4), a job posting, and its extracted requirements. Produce the strongest
honest resume for this posting.

TRUTHFULNESS — these rules override everything else:
1. Use only facts that appear in the library. Never add employers, titles, dates, tools,
   technologies, certifications, metrics, team sizes, scope or outcomes that the cited source
   bullets do not state.
2. Every output bullet must cite 1–2 sourceRefs, and all of them must belong to the entry it is
   listed under (E3.B1 can only appear under E3).
3. Do not introduce any number that is not in the cited sources.
4. You may: rephrase, tighten, reorder clauses, merge two bullets from the same entry, lead with
   the part most relevant to the posting, and use the posting's terminology ONLY when the source
   says the same thing ("Postgres" → "PostgreSQL" is fine; "SQL" → "PostgreSQL" is not).
5. If the candidate lacks something the posting wants, leave it out. Do not imply it.

SELECTION
- Choose the entries and bullets most relevant to the requirements. Omit weak or irrelevant ones.
- Always include EDUCATION entries (bullets optional).
- One page: up to 5 bullets for the most relevant recent role, 2–3 for others, older or less
  relevant roles may have 0–1. Two pages: up to 6 / 4 / 2.
- Order bullets within an entry by relevance to the posting.
- Skills: choose relevant skill refs, grouped into 2–4 categories, most relevant first.

STYLE
- Bullets start with a strong verb, past tense (present tense for a current role), no first
  person, no filler, ideally under 30 words, plain text only (no emojis or special symbols).
- Summary: 2–3 sentences, third-person-implied ("Data analyst with…"), grounded only in the
  library, aimed at this role. No clichés ("results-driven", "passionate", "team player").

MATCH REPORT
- Exactly one requirementMatches item per requirement id.
- "met": the library clearly demonstrates it. "partial": related or adjacent evidence.
  "missing": no evidence. Be strict and honest. "missing" is a useful answer.
- evidenceRefs: the refs that support the verdict ([] for missing). note: one short sentence.
```

The emphasis option is passed as data inside `<options>`. The system prompt's truthfulness rules take priority over anything written in it.

## The fabrication guard (`features/tailor/validate.ts`)

Deterministic checks on `TailorOutput` **before** anything is saved. Pure function, so it gets thorough unit tests (`tests/unit/tailor-validate.test.ts`).

```ts
validateTailorOutput(output: TailorOutput, snapshot: LibrarySnapshot, analysis: JobAnalysis)
  → { output: TailorOutput /* cleaned */, reverts: number, issues: GuardIssue[] }
```

| # | Check | Action |
|---|---|---|
| G1 | `entries[].ref` not in snapshot | Drop the entry |
| G2 | Duplicate entry ref | Keep the first occurrence |
| G3 | Bullet `sourceRefs` that don't exist or belong to another entry | Remove those refs. If none remain, drop the bullet. |
| G4 | Bullet text contains a number not present in its sources (normalise: strip commas/spaces; compare tokens matching `\d+(\.\d+)?%?` and `$`-amounts) | **Revert** to the first source bullet's original text; `reverted = true` |
| G5 | Bullet text empty or > 400 characters | Revert |
| G6 | Two bullets with identical `sourceRefs` | Keep the first |
| G7 | Skill refs not in snapshot | Drop them; drop empty categories |
| G8 | `requirementId` not in analysis | Drop that match |
| G9 | Requirement with no match | Add `{ verdict: "missing", evidenceRefs: [], note: "Not assessed." }` |
| G10 | `evidenceRefs` not in snapshot | Remove. If the verdict is met/partial and no evidence remains → `missing` |
| G11 | EDUCATION entry in snapshot but not in output | Append it (no bullets) |

All guard actions are counted in `TailoredResume.guardReverts` (G4 + G5) and returned as `issues` for logging (codes only, no text).

> The guard catches the mechanical lies (fake numbers, wrong-entry citations, invented skills). It can't catch a rephrasing that subtly overstates. That's what the "show source" popover in the editor and the evals are for.

Cleaned bullets include `reverted`. The model output does not.

Resolved rules:

- Checks run in the order above. The input is left unchanged.
- `reverts` counts bullets restored by G4 or G5. A bullet with both a new number and empty or over-long text is restored once, as G4.
- `issues` are `{ code, ref }` only. The ref is an entry ref, bullet ref, skill ref, or requirement id.
- A source ref is kept only when it is a bullet on that same entry. A repeated ref on one bullet is kept once, in first-seen order.
- G4 reads `$` amounts and numbers, including thousands grouped with commas or spaces (`1,000`, `1 000`) and a trailing `%` (`20%`, `20 %`). Commas and spaces inside the token are removed before comparison. `$50` and `50` are different. `20%` and `20` are different. `2.5` and `2.50` are different. A `+` after a number is not part of the token.
- Restored text is the original text of the first remaining source ref.
- G5 treats whitespace-only text as empty. Length is the raw character count. 400 is kept. 401 is restored.
- G6 treats source refs as a set. Order does not matter. The kept bullet is the first.
- A second match for the same requirement id is dropped and logged as G8.
- Evidence refs may be an entry ref, a bullet ref, or a skill ref. A met or partial verdict with none left becomes missing. The note stays. A missing verdict stays missing. When the model sent no evidence refs at all, the issue ref is the requirement id.
- Omitted education entries are appended in snapshot order with no bullets. Other omitted kinds are not appended here.

## Assembling the editable resume (`features/tailor/assemble.ts`)

`assembleResumeContent(validated, snapshot) → ResumeContent`:
1. Selected entries first, in the AI's order within each kind (code re-sorts kinds into section order; within a kind keep the AI order).
2. Each selected bullet → `{ id: nanoid(), text, included: true, sourceRefs, reverted, edited: false }`.
3. **Unselected library content is included too, switched off:** every snapshot entry not chosen → `included: false` with its original bullets (`included: false`). Every unselected bullet of a chosen entry → appended with `included: false`. This is what lets the user toggle things back in.
4. Summary: `{ text: validated.summary, included: true }`.
5. Skills from refs → names, grouped by the AI's categories.

`assembleResumeContent(validated, snapshot, createId?)`. `createId` defaults to `nanoid`. Tests pass a counter.

Resolved rules:

- Inside a kind, selected entries stay in the model's order. Snapshot entries the model left out follow them, in snapshot order, `included: false`, with their original bullets off.
- A bullet the model cited is not also appended as an off copy. An education entry the guard appended with no bullets gets its original bullets back, switched off.
- The summary is included. Text past 800 characters is cut to 800. Bullet text past 400 characters is cut to 400.
- A skill ref repeated in one category is listed once. A ref that is not on the snapshot is skipped.
- The content stores refs and kinds. Titles, employers, and dates stay on the snapshot.

## Scoring (`features/tailor/score.ts`)

Deterministic and explainable:

```
weight: must = 2, nice = 1        value: met = 1, partial = 0.5, missing = 0
score = round(100 × Σ(weight × value) / Σ(weight))      (null if no requirements)
```

Shown as **Match score**, with the per-requirement breakdown. The score reflects the library, not the resume's wording, so re-tailoring won't game it.

`scoreMatch(analysis, matches) → MatchReport`. `score` is `null` when there are no requirements (`MatchReport.score` is nullable).

Resolved rules:

- `round` is `Math.round`. A value of 12.5 becomes 13. One met must and one missing nice-to-have is `round(200 / 3) = 67`.
- Verdicts follow the analysis order. The first match for a requirement id wins. A requirement with no match is missing, with the note "Not assessed."
- A note past 200 characters is cut to 200.

## Keyword coverage (`features/tailor/keywords.ts`, client + server)

`keywordCoverage(content, snapshot, keywords) → { covered: string[], missing: string[], pct: number }`
- Text = plain-text render of **included** content (summary + entry titles/orgs + bullets + skills).
- Normalise: lowercase; keep `+ # .` (C++, C#, .NET); collapse whitespace.
- A keyword matches if it appears as a whole word or phrase (word-boundary regex with escaped keyword).
- Recomputed on every edit in the resume workspace. Not stored.

Resolved rules:

- The searched text is the included summary, the title and organization of each included entry, included bullets on those entries, and skill names. Dates, locations, and contact details are left out.
- `+`, `#`, and `.` are part of the word. `Java` does not match `JavaScript`, `C++` matches `C++`, and `.NET` does not match inside `ASP.NET`.
- `covered` and `missing` keep the keyword list's spelling and order. `pct` is the rounded share of keywords covered. An empty keyword list yields `0`. A blank keyword is missing.

## Plain text (`features/tailor/plainText.ts`)

`resumePlainText(content, snapshot) → string`. This is the Copy text string (the button lands in T7.2). Included content only. No RoleRefine branding. Same section order as the resume: Summary, Experience, Projects, Education, Certifications, Volunteer, Other, Skills.

```
Morgan Example
Data & reporting analyst
Ottawa, ON · morgan@example.com · 613-555-0100
Portfolio: https://example.com

Summary
Analyst with reporting experience.

Experience
Junior Program Officer
Canada Revenue Agency · Ottawa, ON · 2023-11 – Present
- Maintained 14 reports for a 20-person team.

Skills
Languages: Python, SQL
IBM Cognos
```

Resolved rules:

- The header is name, headline, then location, email, and phone joined with ` · `, then one `Label: url` line per profile link. Empty parts are left out. A link with no label prints the url alone.
- Dates follow the library prompt: an en dash, `Present` for a current role, and `– 2023` when only the end exists. A missing date is left out rather than printed as a dash.
- An included entry with no included bullets still prints its heading. Empty sections are left out. Newlines inside a bullet become one space. Skills with a category print as `Category: A, B`. A blank category prints the names alone.

## 4. COVER_LETTER — library + job + your reasons → letter (1.0)

### Input content

```
<library>{serialized library — same format and refs as TAILOR}</library>
<job>{title, company, requirements with ids, keywords}</job>
<posting>{rawText truncated to 12,000 chars}</posting>
<resume_focus>{if options.resumeId: the refs of the bullets included in that tailor, so the letter aligns with the resume}</resume_focus>
<why_company>{options.whyCompany or "none provided"}</why_company>
<options>Tone: professional | warm | enthusiastic. Length: short (~180 words) | standard (~300 words). Recipient: {name or "Hiring Manager"}. Candidate name: {profile.fullName}.</options>
```

### Output schema (`LetterOutput`)

```ts
z.object({
  greeting: z.string(),
  paragraphs: z.array(z.object({
    text: z.string(),
    sourceRefs: z.array(z.string()),   // library refs (E1.B2, S3) and/or "POSTING" and/or "WHY"
  })),
  closing: z.string(),
  requirementIdsAddressed: z.array(z.string()),
})
```

### System prompt (draft)

```
You write cover letters grounded strictly in the candidate's library.

TRUTHFULNESS (overrides everything):
- Claims about the candidate must come from the cited library refs. Never add employers,
  titles, tools, metrics, or outcomes that are not in those items. No new numbers.
- Claims about the company or role must come from the posting ("POSTING") or the candidate's own
  reasons ("WHY"). Never invent company facts, values, products, news or culture.
- If no reasons are provided, explain interest through the role's responsibilities in the posting.

STRUCTURE: 3–5 paragraphs: (1) the role and a one-line hook connecting the candidate's strongest
relevant experience to the role; (2–3) two or three requirements from the posting matched to
concrete library evidence; (4) why this role/company (from WHY or POSTING); (5) short close
with a call to talk. Every paragraph lists its sourceRefs.

STYLE: match the tone option; first person; plain and specific; no clichés ("I am writing to
express my interest", "passionate", "synergy", "team player"); no flattery; within the target length.
```

### Guard (`features/letters/validate.ts`)
- L1: Unknown refs (not in the snapshot and not `POSTING`/`WHY`) → removed. A paragraph left with no refs is kept only if it's the opening or closing paragraph.
- L2: Number check per **sentence**: every number must appear in the cited library sources, the posting, or the WHY text; otherwise **drop that sentence** and mark the paragraph `reverted: true` (counted in `guardReverts`).
- L3: `WHY` cited but no WHY text provided → remove the `WHY` ref; if the paragraph is about motivation and has no other source, keep it but flag it in the UI ("Add your own reasons to strengthen this").
- L4: `requirementIdsAddressed` filtered to real ids.
- Greeting: `Dear {recipientName or "Hiring Manager"},`. Closing from the model (or `Sincerely,`), and the signature from the profile (never from the model).

Then `assembleLetterContent()` → `CoverLetterContent` (all paragraphs `included: true`).

## 6. PREP_KIT — interview prep (1.1)

**Input:** library (same refs), job analysis, posting, interview kinds already scheduled (to weight technical vs behavioural).

**Output (`PrepKitOutput`):**
```ts
z.object({
  questions: z.array(z.object({
    category: z.enum(["behavioural", "technical", "role", "motivation", "company"]),
    question: z.string(),
    whyAsked: z.string(),
    requirementIds: z.array(z.string()),
    star: z.object({ situation: z.string(), task: z.string(), action: z.string(), result: z.string() }).nullable(),
    sourceRefs: z.array(z.string()),
  })),
})
```

**Prompt rules:** 10–15 questions, at least half tied to must-have requirements; STAR outlines only from cited library items (null if nothing fits, then a tip on how to answer honestly about a gap); never invent results. Company questions are drawn only from posting content.

**Guard:** unknown refs removed; if a STAR outline has no valid refs → `star = null`; any unsupported number in `result` → replace the `result` with `"[Add the measurable result in your own words]"`.

## 7. BULLET_COACH — stronger bullets without invented facts (1.1)

**Input:** one bullet, its entry (title, org, dates), the user's skills list, and the current strength checks that fail.

**Output (`CoachOutput`):**
```ts
z.object({
  suggestions: z.array(z.object({ text: z.string(), why: z.string() })),  // 3
  questions: z.array(z.string()),   // facts to ask the user, e.g. "Roughly how many reports did you automate?"
})
```

**Prompt rules:** rewrite using only facts in the original bullet; where a metric would help, insert a **bracketed placeholder** (`[X%]`, `[number] users`, `[time saved]`) instead of a number; start with a strong verb; under 30 words.

**Guard:** drop any suggestion containing a number (outside `[...]`) that isn't in the original. **UI rule:** a suggestion with placeholders can be applied, but it can't be saved until every `[...]` is replaced by the user.

## Deterministic helpers (no AI)

### Bullet strength → strength (`features/library/strength.ts`)

`bulletStrength(text, skills) → { score: 0–6, tier, passed: CheckId[], fixes: string[] }`

| Check | Pass condition |
|---|---|
| `verb` | First word is in the strong action-verb list (`verbs.ts`, ~150 verbs, incl. present tense for current roles); fails on "Responsible", "Helped", "Worked", "Assisted", "Tasked" |
| `metric` | Contains a digit, %, $, or a multiplier ("2x") |
| `length` | 8–32 words |
| `voice` | No first-person pronouns (I, me, my, we, our) |
| `filler` | None of: "responsible for", "duties included", "various", "etc", "helped with", "tasked with", "worked on" |
| `specific` | Mentions one of the user's skills or a known tool/domain term |

Tier: 0–2 **Weak** · 3 **Fair** · 4 **Good** · 5 **Strong** · 6 **Excellent**. Used by the strength meters, library health, the free Bullet Strength Checker, and the resume workspace. Table-driven unit tests (≥ 30 cases).

Resolved rules:

- `skills` is the user's skill names. A match is case-insensitive and must be a whole word or phrase, so `Java` does not match `JavaScript` and a one-letter skill matches only as its own word.
- `verbs.ts` includes past and present (`Led` and `Lead`) and both `-ize` and `-ise`. The first word is compared with surrounding punctuation removed. The check does not receive whether the role is current; present-tense verbs are in the list so those bullets can pass.
- A metric is a digit, `%`, `$`, or a multiplier such as `2x` or `2 x`. Words are split on whitespace; 8 and 32 both pass `length`.
- First person is `I`, `me`, `my`, `we`, `our`, including contractions (`I'm`, `I've`, `I'd`, `I'll`, `we're`, `we've`, `we'd`, `we'll`). `i.e.`, `your`, `image`, and `us` do not fail `voice`.
- Filler phrases match as whole words. The fix quotes the first phrase found, in the order listed above.
- `specific` also accepts `KNOWN_TERMS` in `strength.ts` (SQL, Excel, Python, React, AWS, and the rest of that list).
- Each fix names the next tier: Weak → Fair, Fair → Good, Good → Strong, Strong → Excellent. Excellent has no fixes.
- The meter draws 5 segments, one per tier. Weak fills 1 and Excellent fills 5. Hover and keyboard focus show the fixes.

## Evals (`evals/`)

Run before merging any change to prompts, schemas, models, or effort.

- `evals/fixtures/libraries/*.json`: 4 fake personas as `LibrarySnapshot`s (new CS grad; BI/reporting analyst moving to dev; mid-level frontend dev; career changer from retail). Skips IMPORT so runs are cheap and repeatable.
- `evals/fixtures/postings/*.txt`: 6 real-style postings (junior dev, data analyst, frontend, government IT developer, support engineer, product-y role).
- `evals/fixtures/resumes/*`: 3 fake resumes (PDF/DOCX/text) for IMPORT runs. Reuse and expand v1's `backend/tests/static/` files.
- `npm run evals` → for each library × posting: ANALYZE + TAILOR + guard + score, plus COVER_LETTER for half the pairs (with and without WHY text). Writes `evals/out/<timestamp>/<pair>.json` (gitignored) and prints a table:

  `pair | reverts | dropped bullets | match score | words | seconds | $cost`

- **Manual rubric** (read 5 random pairs per run): (1) any claim not supported by its source? (2) were the most relevant items selected? (3) does it read like a strong human-written resume? (4) is the summary grounded?
- **Fail conditions:** any fabrication found manually → fix the prompt before merging. Average reverts per tailored resume > 0.5 → tighten the prompt.
- Full run cost: roughly 24 tailored resumes ≈ $1.50.
